2. Explicit Functional Dependencies (FDs)

An attribute $Y$ is functionally dependent on $X$ ($X \rightarrow Y$) if each value of $X$ determines exactly one value of $Y$.

Academics Schema Functional Dependencies:
  • Department: dept_id → {dept_code, dept_name, office_location, contact_email}
  • Program: program_id → {dept_id, program_code, program_name, total_semesters, total_credits}
  • Semester: semester_id → {term_name, academic_year, start_date, end_date}
  • Student: student_id → {roll_number, user_id, program_id, first_name, last_name, email, cnic, phone, admission_date}
  • Section: section_id → {course_id, semester_id, teacher_id, section_name, max_capacity, room_number}
  • Enrollment: {student_id, section_id} → {enrollment_id, enrollment_date, status, final_grade, gpa_points}
  • Assessment: assessment_id → {section_id, title, assessment_type, max_marks, weightage_percent}
  • Result: {assessment_id, enrollment_id} → {marks_obtained, remarks, graded_at}
Finance & Inventory Functional Dependencies:
  • Fee Structure: {program_id, semester_id} → {tuition_fee, lab_fee, library_fund, exam_fee}
  • Invoice: invoice_id → {student_id, semester_id, fee_structure_id, total_amount, balance_due}
  • Book Copy: barcode → {copy_id, book_id, edition, shelf_location, status}
  • Room/Lab: {dept_id, room_number} → {room_id, room_name, room_type, capacity}
3. Anomalies in Unnormalized Design

If college data were stored in a single flat table FLAT_ENROLLMENT(roll_no, student_name, dept_name, course_code, teacher_name, teacher_office), three anomalies occur:

Insertion Anomaly

Cannot add a newly hired Teacher or a new Department until at least one Student enrolls in their course, because the composite key (roll_no, course_code) cannot be NULL.

Deletion Anomaly

If the only student enrolled in a specialized course drops out and their row is deleted, the course description, teacher record, and office details are accidentally wiped from the database.

Update Anomaly

If Professor changes office room, it must be updated across thousands of enrollment tuples. Any missed update produces contradictory records.

4. Step-by-Step Normalization Proof (1NF → BCNF)

  • Condition: All column attributes contain atomic (indivisible) domain values. No comma-separated strings or arrays.
  • Applied: Multi-valued student phone numbers and multiple courses enrolled are exploded into atomic relations with unique scalar keys.

  • Condition: Relation is in 1NF and no non-prime attribute is partially dependent on a proper subset of any candidate key.
  • Applied: In ENROLLMENT(student_id, section_id, grade, section_capacity), section_capacity depends only on section_id (partial dependency). We split into ENROLLMENT and SECTION.

  • Condition: Relation is in 2NF and has no transitive dependencies ($X \rightarrow Y$ and $Y \rightarrow Z$).
  • Applied: Student contains student_id → program_id and program_id → dept_id → dept_name. Transitive chain is removed by separating into student, program, and department.

  • Condition: For every non-trivial functional dependency $X \rightarrow Y$, $X$ must be a superkey of the relation.
  • Applied: All 25 relations in AcademiaPro strictly adhere to BCNF because every determinant is an explicit surrogate or natural candidate superkey.
5. Formal Relational Mathematical Model

Relational operations are formally Cartesian products filtered by selection ($\sigma$) and projection ($\pi$):

STUDENT ⊆ D_ID × D_ROLL × D_NAME × D_EMAIL × D_STATUS
ENROLLMENT ⊆ STUDENT × SECTION → GRADE × STATUS
ASSESSMENT_RESULT ⊆ ENROLLMENT × ASSESSMENT → SCORE

Referential Integrity Constraint: ∀ e ∈ ENROLLMENT, ∃ s ∈ STUDENT such that e.student_id = s.student_id.
